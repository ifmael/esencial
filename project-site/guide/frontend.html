Frontend: React sin estado global

7 pantallas, react-router 7 en modo declarativo, Tailwind 4, y una regla de oro: cada pantalla es dueña de sus datos. No hay Redux, no hay Context de datos, no hay cache client. Un hook por pantalla, un fetch, estado local.

2. El patrón de datos: hooks por pantalla

Cada pantalla tiene un hook que encapsula su única fuente de datos. Este es useDay, corazón de la app:

export function useDay(date: string): DayState {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [nonce, setNonce] = useState(0);
  const current = useRef(date);
  current.current = date;                    // el ref SIEMPRE sabe la fecha viva

  useEffect(() => {
    let live = true;
    setData(null);                           // nada de datos rancios mientras carga
    setLoading(true);
    fetch(`/api/day/${date}`)
      .then((res) => res.json())
      .then((d) => {
        if (live && current.current === date) setData(d);  // descarta respuestas viejas
      });
    return () => { live = false; };          // cleanup al desmontar/cambiar fecha
  }, [date, nonce]);

  return { data, loading, error, reload: () => setNonce((n) => n + 1) };
}

Fuente: web/src/lib/day.ts. Fíjate en current.current === date: si navegas rápido entre días, la respuesta lenta del día viejo se descarta. Es el bug clásico de race condition, resuelto en 3 líneas.

3. Autosave de la nota: debounce + desmontaje

La nota del día se guarda sola. El truco está en cómo el padre monta el editor:

// El padre lo monta con key={date}: al cambiar de fecha, el desmontaje
// guarda lo pendiente contra la fecha VIEJA (closure de `date`),
// y el editor nuevo arranca con la nota de la fecha nueva.
<NoteEditor key={date} date={date} initial={note.text} />

// dentro de NoteEditor: debounce de 800ms + flush en unmount
useEffect(() => {
  if (!dirty) return;
  const t = setTimeout(() => apiSend(`/api/notes/${date}`, "PUT", { text }), 800);
  return () => clearTimeout(t);

Fuente: web/src/routes/dia.tsx. Nada de "guardar" manual: escribes, esperas 0.8s, guardado.

4. Sin optimismo: PUT semanal completo

El plan de comidas hace algo deliberadamente aburrido (decisión D6 del design): cada cambio persiste con un PUT de la semana entera y el estado local se reemplaza con la respuesta del servidor. Sin actualizaciones optimistas, sin diffs:

const save = useCallback(async (next: Slot[]) => {
  const ok = await apiSend(`/api/meal-plan/${isoWeek}`, "PUT", { slots: next });
  if (!ok) refetch();   // PUT fallido → recarga el estado real del servidor
}, [isoWeek]);
Filosofía del repo: para una app de 1 usuario, la simplicidad de "el servidor siempre gana" vale más que la fluidez del optimismo. El único draft en memoria es el de la sesión de gym (estado A → B al cerrar).
