Modelo de datos: 13 tablas y una idea

SQLite puro, sin ORM. Cada dominio (recetas, ejercicios, plantillas, semanas) tiene sus tablas; los planes referencian catálogos; los logs congelan lo ejecutado. Lo efímero (lista de compra) no se guarda.

1. Cómo se conectan las piezas

Verde = catálogos que editas · Azul = planes que decides · Verde oscuro = historia que se congela.

2. Las tres reglas del esquema

🔗 Claves foráneas con intención

ON DELETE CASCADE para piezas dependientes (borras la receta → se van sus ingredientes); ON DELETE RESTRICT para referencias valiosas (no puedes borrar un ejercicio usado en plantillas).

✅ CHECK como contrato

El esquema valida dominio: effort BETWEEN 1 AND 5, meal IN ('desayuno','almuerzo','cena'), status IN ('planned','logged'). La BD rechaza lo que ni Zod debería aceptar.

🧊 Un log por sesión

plan_sessions.date UNIQUE + workout_logs.plan_session_id UNIQUE: la BD misma impide registrar un día dos veces — el 409 que verás en la API nace aquí.

3. El truco del esquema: snapshot por FK

Un log de entrenamiento no guarda el nombre del ejercicio — guarda el template_exercise_id. El registro es vista de la plantilla en ese momento:

CREATE TABLE IF NOT EXISTS set_logs (
  id                   INTEGER PRIMARY KEY,
  workout_log_id       INTEGER NOT NULL REFERENCES workout_logs(id) ON DELETE CASCADE,
  template_exercise_id INTEGER NOT NULL REFERENCES template_exercises(id) ON DELETE RESTRICT,
  set_index            INTEGER NOT NULL,
  weight_kg            REAL,
  reps                 INTEGER,
  done                 INTEGER NOT NULL DEFAULT 0
);
Lectura del diseño: si mañana cambias la plantilla "A — Empuje", los logs antiguos no se corrompen (apuntan a filas concretas, y RESTRICT impide borrarlas). Es la versión barata de "congelar": en vez de copiar datos, referencias filas protegidas.

4. Migraciones: el baseline + additivos

schema.sql es el estado v1 completo (idempotente, CREATE TABLE IF NOT EXISTS). Los cambios nuevos son migraciones numeradas que el runner de D1 aplica exactamente una vez:

-- api/migrations/0003_e3_shopping.sql (E3)
CREATE TABLE IF NOT EXISTS shopping_items (
  id           INTEGER PRIMARY KEY,
  week_plan_id INTEGER NOT NULL REFERENCES week_plans(id) ON DELETE CASCADE,
  position     INTEGER NOT NULL,
  food         TEXT NOT NULL,
  quantity     REAL, unit TEXT, section TEXT,
  checked      INTEGER NOT NULL DEFAULT 0
);
ALTER TABLE recipe_ingredients ADD COLUMN section TEXT;

Fuente: api/schema.sql y api/migrations/. En D1 el "si ya existe, no hagas nada" lo da la tabla _cf_D1_MIGRATIONS, no el SQL.
