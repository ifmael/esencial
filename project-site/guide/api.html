11 grupos de rutas bajo /api/*. Toda mutación pasa por un esquema Zod; todo error es {error, field?}; todo handler corre dentro de guard(). Nada más que aprender.

2. La anatomía de un endpoint (la verás 20 veces)

Todos los handlers siguen el mismo esqueleto de 4 pasos. Este es PUT /api/notes/:date, el más corto:

.put("/:date", zBody(dayNoteSchema), (c) =>          // 2. valida el body con Zod
  guard(async () => {                                 // 4. convierte errores SQL en 500 seguros
    const date = c.req.param("date");
    if (!DATE.test(date)) return fail("date must be YYYY-MM-DD", "date");  // 1. valida el path
    const input = c.get("validated");                 // body ya parseado por zBody
    await c.env.DB.prepare(
      `INSERT INTO day_notes (date, text) VALUES (?, ?)
       ON CONFLICT(date) DO UPDATE SET text = excluded.text`,
    ).bind(date, input.text).run();
    return json({ date, text: input.text });
  }),
)

Fuente: api/src/routes/notes.ts. zBody es middleware: si Zod falla, ni entra al handler.

3. Fail-closed: Zod en la puerta

Ningún JSON llega a la BD sin pasar por un esquema. El error lleva el campo exacto que falló, para que la UI lo pinte junto al input:

// api/src/http.ts
export async function readValidated<T>(req, schema) {
  let raw;
  try { raw = await req.json(); }
  catch { return { ok: false, res: fail("Invalid JSON body", "body") }; }
  const parsed = schema.safeParse(raw);
  if (!parsed.success) {
    const issue = parsed.error.issues[0];
    const field = issue?.path.length ? issue.path.map(String).join(".") : undefined;
    return { ok: false, res: fail(issue?.message ?? "Invalid input", field) };
  }
  return { ok: true, data: parsed.data };
}

// el contrato de error de TODA la API:
fail("date must be YYYY-MM-DD", "date")
// → 400 {"error":"date must be YYYY-MM-DD","field":"date"}

4. El endpoint más interesante: /api/day/:date

La pantalla "Hoy" necesita 3 cosas. Podrían ser 3 peticiones; es 1 con tres queries SQL que se agregan en el Worker:

// comidas del día: LEFT JOIN para que un slot con receta borrada
// se lea como {recipeId: null} en vez de romper
const meals = await rows(db,
  `SELECT ms.meal, ms.recipe_id AS recipeId, r.name AS recipeName
   FROM meal_slots ms
   JOIN week_plans wp ON wp.id = ms.week_plan_id
   LEFT JOIN recipes r ON r.id = ms.recipe_id
   WHERE wp.iso_week = ? AND ms.day = ?`, isoWeek, dayIndex);

// sesión programada + resumen del log (ejercicios, series, esfuerzo)
const session = await row(db, `SELECT ps.id, ps.status, ... , wl.effort,
    COUNT(DISTINCT sl.template_exercise_id) AS exercises, COUNT(sl.id) AS sets
  FROM plan_sessions ps ... LEFT JOIN workout_logs wl ON wl.date = ps.date ...`);

const note = await row(db, "SELECT text FROM day_notes WHERE date = ?", date);
return json({ date, isoWeek, dayIndex, meals, session, note });

Fuente: api/src/routes/day.ts. Regla del spec: "missing data is empty data, not errors" — un día vacío es un 200 con arrays vacíos.

6. Errores SQL → respuestas humanas

El onError global traduce los errores de SQLite a mensajes que la UI puede mostrar. Fíjate en el patrón UNIQUE:

export function dbFailure(err) {
  const message = err instanceof Error ? err.message : "";
  const m = /UNIQUE constraint failed: \w+\.(\w+)/.exec(message);
  if (m) return fail("Already exists", m[1]);        // 400 con el campo duplicado
  if (/FOREIGN KEY constraint failed/.test(message))
    return fail("References a missing or in-use record", "reference");
  return json({ error: "Internal server error" }, 500); // nunca filtra SQL
}

Fuente: api/src/http.ts. Un POST /api/recipes con nombre repetido devuelve 400 {"error":"Already exists","field":"name"} — y la UI lo muestra junto al input.

Regla mental: 400 = tu JSON no valida · 401 = sin sesión · 404 = no existe · 409 = el día ya está registrado · 500 = fallo interno (mensaje genérico). Nada más.
