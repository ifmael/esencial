Arquitectura: un Worker lo es todo

No hay servidor de Node, ni nginx, ni Docker. Hay un único Cloudflare Worker que hace tres trabajos: servir la SPA compilada, atender la API en /api/* y hablar con SQLite en D1. Todo el repo existe para construir eso.

1. El mapa completo

El Worker decide: rutas /api/* → Hono → D1; todo lo demás → assets de la SPA.

caja = componente real del repo → flujo de petición zona = proceso desplegado

2. wrangler.toml — el corazón del despliegue

Este archivo dice Cloudflare qué desplegar. Dos detalles clave: run_worker_first = true (el Worker inspecciona todas las peticiones, necesario para proteger páginas HTML) y not_found_handling = "single-page-application" (los deep links como /plan-fuerza caen en index.html).

name = "esencial"
main = "api/src/index.ts"          # el Worker ES este archivo

[assets]
directory = "./web/dist"           # la SPA compilada vive aquí
binding = "ASSETS"
run_worker_first = true            # el Worker ve TODAS las peticiones
not_found_handling = "single-page-application"

[[d1_databases]]
binding = "DB"                     # c.env.DB en el código
database_name = "esencial"
migrations_dir = "api/migrations"

Fuente: wrangler.toml en la raíz del repo.

3. El punto de entrada: 40 líneas que lo conectan todo

const app = new Hono<{ Bindings: Env }>()
  .use(securityHeaders)   // CSP + nosniff en TODAS las respuestas
  .use(authGuard)         // /api/* exige cookie válida (401)
  .use(pageGuard)         // páginas HTML sin sesión → 302 /login
  .route("/api", api)
  .notFound(async (c) => {
    if (c.req.path.startsWith("/api")) return json({ error: "Not found" }, 404);
    // deep links caen aquí: re-sirve el asset (index.html del SPA router)
    const asset = await c.env.ASSETS.fetch(c.req.raw);
    return new Response(asset.body, asset);
  })
  .onError((err, c) => dbFailure(err));   // 500 genérico, sin filtrar SQL

Fuente: api/src/index.ts — el orden de los use() importa: primero cabeceras de seguridad, luego autenticación.

4. Los tres middlewares, en orden

middlewaretrabajosi falla
securityHeadersCSP estricta (default-src 'self'), nosniff, referrer policynunca — solo añade cabeceras
authGuardprotege /api/* salvo /api/auth/* y GET /api/health401 {error:"Unauthorized"}
pageGuardprotege HTML (UX, no seguridad): rutas sin punto ni sesión302 → /login?next=…
Por qué dos guardas: la de la API protege datos (la real); la de páginas solo evita que un visitante vea el HTML vacío antes del 401. El spec E7 las llama "defense-in-depth": el cliente también redirige, pero el servidor manda.

5. Sesión sin base de datos: HMAC firmado

No hay tabla de sesiones. La cookie esencial_session contiene la fecha de expiración firmada con HMAC-SHA256 usando AUTH_SECRET (un secreto del Worker). Verificarla es local y instantáneo:

// el valor: "<exp_epoch>.<hmac(secret, exp_epoch)>" — 30 días, renovación = re-login
export async function readSessionToken(secret, raw) {
  const parsed = await parseSigned(`esencial_session=${raw}`, secret, "esencial_session");
  const value = parsed["esencial_session"];
  if (value === false || value === undefined) return null;   // manipulada
  const exp = Number(value);
  if (!Number.isInteger(exp) || exp * 1000 <= Date.now()) return null; // caducada
  return { exp };
}

Fuente: api/src/auth.ts. Las contraseñas van con PBKDF2-SHA256 (100k iteraciones) y comparación en tiempo constante vía crypto.subtle.verify.

6. Del código al mundo: el pipeline

pnpm dev                  # wrangler dev: Worker + D1 local (data/ esencial.db local)
pnpm db:migrate:local     # aplica api/migrations/*.sql a la D1 local
pnpm build                # compila la SPA a web/dist (vite)
pnpm deploy               # build + wrangler deploy (el Worker y los assets juntos)
Local ≠ producción solo en la BD: el mismo código de Worker corre en wrangler dev y en Cloudflare; la D1 local es un SQLite en disco. Las migraciones se aplican por separado en cada mundo.
