Operación

Deploy

Un Worker, dos bindings y dos secretos. El deploy lo hace Cloudflare, no GitHub: un push a main dispara Workers Builds, que construye el SPA y publica el Worker. GitHub Actions corre en paralelo y solo verifica — nunca despliega, y el deploy no espera su resultado.

Clave de wrangler.toml Valor Por qué
mainapi/src/index.tsEl Worker es el único punto de entrada.
[assets] directory./web/distSirve el SPA construido, sin servidor aparte.
[assets] bindingASSETSEl Worker lee los assets con env.ASSETS.fetch.
run_worker_firsttrueSin esto el Worker no vería las peticiones de páginas y pageGuard sería inútil.
not_found_handlingsingle-page-applicationLos deep links caen a index.html y routeriza el SPA.
[[d1_databases]]binding DB → esencialBase de datos; migrations_dir = "api/migrations".
[[r2_buckets]]binding PHOTOS → esencial-photosFotos de recetas; sin el bucket creado, el deploy falla.
compatibility_date2026-08-31Fija el comportamiento del runtime.

No hay [vars]: los secretos no viven en el repositorio. En producción entran por wrangler secret put; en local, por .dev.vars en la raíz, que está ignorado por git y lo genera predev.

Los pasos, en orden

Cuándo Qué Cómo
Una vez Autenticar wrangler y crear la base npx wrangler login · npx wrangler d1 create esencial
Una vez Crear el bucket de fotos npx wrangler r2 bucket create esencial-photos
Una vez, y al rotar Secretos de acceso openssl rand -base64 24 | npx wrangler secret put AUTH_SECRET
node api/scripts/hash-password.ts 'tu-clave' | npx wrangler secret put PASSWORD_HASH
Cada deploy Publicar Push a main (automático) o pnpm run deploy (manual)
Si cambia el esquema Aplicar migraciones pnpm db:migrate:remote — justo después del deploy
Post-deploy Comprobar Los cinco curl de abajo
Si algo va mal Revertir npx wrangler rollback o el botón «Rollback» del deployment

El deploy no aplica el esquema. Publicar código y migrar la base son dos operaciones distintas, y el orden importa: 0009_fuerza_v2 recrea las tablas de planificación de fuerza, así que se pierde el histórico de sesiones y entrenamientos. Se ejecuta justo después del deploy, cuando ya no queda nadie escribiendo en el esquema viejo.

Verificación en dos minutos

# 1. sin sesión, la raíz redirige al login
curl -i https://esencial.<sub>.workers.dev/                     # → 302 a /login?next=%2F

# 2. la sonda de salud está abierta
curl https://esencial.<sub>.workers.dev/api/health             # → 200 { ok: true }

# 3. la API sin cookie cierra la puerta
curl -i https://esencial.<sub>.workers.dev/api/recipes          # → 401 { error: "Unauthorized" }

# 4. en el navegador: /login → entra con tu contraseña → carga el DÍA
# 5. «Cerrar sesión» → vuelve a /login, y con la cookie vieja los curl dan 401

Rollback

Qué revierte

Solo el código del Worker: vuelve a la versión anterior. La base de datos no se toca, porque el esquema es aditivo e idempotente — salvo las migraciones marcadas como destructivas, que no tienen vuelta atrás.

Cerrar el acceso ya

Rotando AUTH_SECRET: todas las cookies emitidas dejan de verificar al instante, sin desplegar nada. Es el interruptor de emergencia.

Fuentes: wrangler.toml, DEPLOY.md (pasos 1-7 y rollback), package.json, AGENTS.md §1, §4 y §5, .github/workflows/ci.yml. Los pasos manuales son los que describe DEPLOY.md; el id de la base y el nombre del bucket están en el wrangler.toml del repositorio.
