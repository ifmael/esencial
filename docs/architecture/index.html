Visión general

Esencial, de arriba abajo

Esencial es una app de bienestar personal —recetas, plan semanal y plan de fuerza— que vive en dos Workers de Cloudflare: el frontal sirve los assets del SPA y protege el HTML, y la API atiende /api/*. El navegador habla con los dos —la API con CORS y credenciales— y ambos comparten una única base D1 y un bucket R2 para las fotos de recetas.

Quién contesta a cada dirección

Hay dos programas y dos despliegues: el Worker frontal entrega los archivos de la aplicación y el Worker de la API responde con datos. Al abrir una dirección, el navegador pide el documento a https://esencial.nutrirutina.workers.dev, y la aplicación llama después a https://esencial-api.nutrirutina.workers.dev con CORS y credenciales.

En el dist no hay un archivo por pantalla

Lo que se publica son tres cosas y poco más. No hay una carpeta plan-fuerza ni un recetario.html: 

web/dist/
├─ index.html               ← el único documento: el esqueleto de la app
└─ assets/
   ├─ index-<código>.js     ← el programa que corre en el navegador
   └─ index-<código>.css    ← los estilos

Cuando pides una pantalla como /plan-fuerza, pasan tres cosas:

  1. El programa busca ese archivo entre los suyos y no lo encuentra.
  2. Está configurado para que, si no lo encuentra y la dirección no empieza por /api/, entregue index.html.
  3. El programa que va dentro de ese documento lee la dirección y pinta la pantalla de Plan fuerza.

Es decir: todas las pantallas devuelven el mismo documento. Por eso el control de acceso ocurre antes de la entrega y no dentro de la aplicación — dentro ya no habría nada que evitar, la descarga ya habría pasado.

Dos momentos distintos

  • Primera entrega — primera visita, recarga, enlace pegado o un dispositivo nuevo: el navegador pide el documento al frontal, y ahí actúa su guard; las llamadas a /api/* pasan por authGuard.
  • Aplicación ya abierta — moverse entre pantallas no pide ningún documento: el control lo hace la propia app preguntando por /api/auth/status.

La API no pide los datos por la red

El código de la API lee la base y las fotos directamente, con los enlaces que Cloudflare le da a su Worker (DB y PHOTOS), no pidiendo otra URL. Lo que sí cruza la red es la llamada del navegador: el SPA llama a la API por su URL absoluta (VITE_API_URL, fijada en el build) con credentials: "include", así que la API autoriza el origen de la web con CORS y el frontal autoriza el origen de la API en su CSP (connect-src e img-src). La cookie de sesión la emite la API y en workers.dev lleva Domain=nutrirutina.workers.dev, para que el guard del frontal también pueda verla.

Compruébalo en 30 segundos. Ejecuta pnpm build y luego ls web/dist web/dist/assets: verás index.html, el JavaScript y el CSS. Ninguna carpeta por pantalla.

Las cinco decisiones que explican esta arquitectura

Todo lo demás en este sitio es consecuencia de estas cinco. Cada una tiene su sección.

  1. Dos Workers: uno para la web y otro para la API. El wrangler.toml de la raíz fija el frontal (assets de web/dist, binding ASSETS, run_worker_first = true y el guard del HTML en web/worker/index.ts); api/wrangler.toml fija la API (Hono, D1 y R2). El navegador habla con los dos, así que el CORS es explícito y con credenciales.
  2. Cada Worker protege lo suyo. El frontal aplica las cabeceras y el guard del HTML en web/worker/index.ts; la API aplica securityHeaders, cors y authGuard en api/src/middleware.ts antes de las rutas, así que ninguna ruta nueva puede nacer desprotegida por descuido.
  3. D1 es la única fuente de verdad, y se versiona por migraciones numeradas. api/schema.sql es el estado final; 0001 es el baseline congelado y los cambios viven en deltas (aditivos o destructivos) con su propio número.
  4. La sesión-día es la unidad de planificación (Fuerza v2). Una plantilla es una agrupación semántica que se expande en el día y desaparece como entidad; lo duradero es el día. Se aplica con UNIQUE en base, validación en la API y bloqueo en la UI.
  5. El gate es un test que falla primero. TDD en cada cambio, y CI que ejecuta typecheck, test, e2e y lint en dos jobs de GitHub Actions antes de tocar main.
