01 · El mapa

Siete estaciones, tres carriles y una regla

El recorrido no es una caja negra: cada estación deja un rastro y se puede parar. Las tres primeras ocurren en tu ordenador; las dos siguientes son ayudantes; la sexta es la propuesta; la séptima eres tú.

Tú decides

Qué se quiere, cuándo está listo y cuándo se publica. El ayudante nunca se autopromociona.

El conductor ordena

run prepara la copia, llama a las cajas en orden y se detiene cuando hace falta una persona.

Las cajas trabajan

Implementar, comprobar y revisar ocurren en entornos aislados; no ven tus llaves ni tu repositorio principal.

04 · Las piezas

Qué hace cada pieza y qué no hace

La seguridad del flujo depende de que cada pieza tenga un trabajo pequeño y un límite claro.

Conductor

run

Prepara la copia, llama a las fases en orden, espera los resultados y se detiene en un bloqueo o en tu validación.

No hace: no escribe código, no revisa, no aprueba y no mergea.

Memoria

La libreta

Guarda la fase, las rondas y la huella de lo aprobado en ~/.orquestator/ESQ-123/.

No hace: no vive dentro de la copia; el implementador no puede reescribirla.

Disco

La copia

Una copia de trabajo con su propia historia, sin conexión directa con tu repositorio principal.

No hace: no monta tu .git principal ni empuja a la rama principal.

Frontera

El espejo

Una copia de la rama principal de solo lectura. El implementador la trae y resuelve los choques.

No hace: no escribe en tu repositorio; el host lo actualiza.

Aislamiento

Las cajas

Cada fase corre en una caja con las herramientas que necesita y solo los ficheros que le tocan.

No hace: no ve tus llaves, tu repositorio principal ni la libreta.

Freno

El control de zonas

Muestra el cambio de las zonas delicadas, pide una aprobación humana con huella y publica el semáforo guard.

No hace: no aprueba solo; el ayudante no puede aprobar.

Robot

Las comprobaciones

Estilo, tipos, pruebas, cobertura y recorrido completo. Comprueba que la prueba nuevo falla antes del arreglo.

No hace: no opina sobre el diseño; si algo falla, vuelve al implementador.

Ojos nuevos

Los revisores

Uno revisa antes de la propuesta; otro revisa la propuesta publicada. El segundo ve el cambio, no el hilo de comentarios.

No hace: no ve la conversación del implementador ni puede tocar el código.

Base de datos

La migración

Un robot de comprobaciones comprueba el estado con una llave de solo lectura; el conductor aplica el cambio tras tu aprobación con una llave de edición.

No hace: no se aplica sola, no tiene vuelta atrás automática y no se toca desde una copia temporal.

Opcional · M5a

La copia temporal

Una web y una base de datos solo para esa propuesta, con Access y datos sembrados.

No hace: no usa la base de datos ni las fotos de producción.

Después

La limpieza

Retira la copia, la libreta y la caja; comprueba el despliegue y sugiere volver atrás si algo falla.

No hace: no borra la propuesta ni tu rama remota.

05 · Aprobaciones

El semáforo va atado a la versión exacta

Una etiqueta se queda pegada a la propuesta aunque cambie el código. Un semáforo no: cada versión tiene el suyo. Por eso lo delicado se aprueba con una huella.

Antes de subir

Manda la huella

El control compara el cambio con la lista de zonas delicadas. Si hay algo, el flujo se para y te enseña el cambio. Tú ejecutas approve en una terminal interactiva; se guarda una huella del cambio en la libreta de tu ordenador.

Antes de las comprobaciones y de la propuesta, el conductor exige esa huella. No hay un número remoto todavía: la rama aún no se ha subido.

Después de subir

Manda el semáforo

Justo después de subir la rama, si la huella sigue coincidiendo, el conductor publica el semáforo guard sobre esa versión exacta. La protección de la rama principal y el trabajo automático de comprobaciones lo ven.

Si un fix cambia el cambio, el semáforo anterior deja de valer. El conductor revalida la huella: si no coincide, vuelve a Blocked; si coincide, lo vuelve a publicar.

  1. El cambio toca una zona delicada

    La lista vive en orquestator-cli/protected-paths.txt y se lee de tu copia principal, no de la rama.

  2. El conductor se detiene y te enseña el cambio

    La tarea pasa a Blocked; se te asigna y se te menciona. No se abren comprobaciones ni propuesta sin tu sí.

  3. Tú apruebas en una terminal

    approve guarda el motivo y una huella del cambio en la libreta de tu ordenador. Si el cambio cambia, la aprobación caduca.

  4. Se comprueba y se sube

    El conductor exige la huella en local; tras subir la rama publica el semáforo guard en la versión exacta.

  5. Una subida nueva invalida el semáforo

    Si el cambio protegido cambió, vuelve a Blocked. Si no cambió, el conductor repone el semáforo.

  6. Las automatizaciones de GitHub no son aprobables

    Un cambio en .github/workflows/ va en una propuesta tuya, fuera del flujo. La llave del conductor no tiene permiso de workflows.

Propuestas manuales: si abres una propuesta tú (por ejemplo, para cambiar las comprobaciones), puedes aprobar sus zonas delicadas con approve --pr N. El semáforo se publica sobre esa versión; si añades commits, se invalida y se vuelve a aprobar.

06 · Migraciones

Cambiar la base de datos sin pisar a nadie

Una migración es un cambio de estructura o de datos. No se aplica sola, no se puede deshacer con un botón y tiene que coordinarse con las demás tareas.

  1. El cambio toca api/migrations/

    La tarea lleva la etiqueta migración y una checklist en la propuesta. Es un cambio delicado: se aprueba aparte.

  2. El robot de comprobaciones mira si hay migración

    El trabajo automático migracion corre en todas las propuestas con una llave de solo lectura. Si no hay migración, pasa; si hay, comprueba que esté aplicada en la base de datos real.

  3. La tarea se para y te pide aprobación

    Sin approve --migracion, no se aplica nada. El conductor te pide el sí en una terminal interactiva.

  4. El conductor aplica la migración

    Con una llave de edición limitada a la base de datos y a los scripts de Cloudflare, y un wrangler fijado. Nunca se usa wrangler login ni una llave global de la cuenta.

  5. Se vuelve a lanzar el robot

    El trabajo automático migracion se re-ejecuta. Solo cuando pasa, junto con las comprobaciones de integración y estilo, la tarea puede pasar a In validation.

  6. Si una migración ya aplicada cambia de huella

    El conductor bloquea. Una migración aplicada es inmutable: el arreglo va en una migración nueva. La base de datos no tiene un botón de deshacer.

El atasco que se corrigió: antes, la revisión de la propuesta esperaba todas las comprobaciones en verde, incluido migracion, pero la migración se aplicaba «dentro» de In validation. Ninguno de los dos pasos podía ocurrir primero. Ahora se aprueba y se aplica antes de In validation; el robot confirma y entonces se mueve el estado.
M5a · copia temporal

Primero la base de datos de prueba

La migración se aplica a la base de datos de la copia temporal antes de construir y publicar esa copia. Nunca se usa la base de datos de producción para una copia temporal.

Producción

Después, la base de datos real

La base de datos real se toca solo después de tu approve --migracion y antes de In validation. El merge no aplica migraciones por sorpresa.

M0 · Base 0,3-0,5 día · sin dependencias

Dejar listas las cuentas y la configuración mínima. No se escribe código de producto.

  • gh auth login y Docker funcionando.
  • Repo público y protección de la rama principal: propuesta de cambio obligatoria, comprobaciones ci, lint y migracion, sin bypass.
  • Trabajo automático migracion en las comprobaciones con una llave de Cloudflare de solo lectura; verificar que puede listar las migraciones. Si no, se usa el plan B (el conductor publica el estado para todas las propuestas).
  • Llave de edición para el conductor (base de datos + scripts), llave de Linear, secretos de Dependabot si se usa.
  • Workspace de Linear con los estados y la vista «Necesita mi decisión»; sin una etiqueta aparte: el semáforo lo publica el conductor.
  • docs/flujo.md, .gitignore con .task/ y revisión previa a hacer público el repo.

Hecho cuando: una tarea de prueba se crea en Linear, se lee con curl y una rama empujada aparece enlazada.

M1 · Imagen del worker 0,5 día · depende de M0

Una imagen reproducible con todo lo que necesitan las cajas. La imagen lleva herramientas, no código.

  • Node 24, pnpm con store caliente, Chromium/Playwright, Hermes fijado y wrangler.
  • Proxy de modelo con la llave real; dentro de la caja, una llave falsa.
  • Red interna, --network none para las comprobaciones, WRANGLER_SEND_METRICS=false.
  • Límites de CPU, memoria y procesos; usuario no-root; cap-drop=ALL; no-new-privileges.
  • Provider de nan dentro del Hermes de la caja apuntando al proxy; consulta de prueba.
  • Etiqueta de imagen por Dockerfile + pnpm-lock.yaml.

Hecho cuando: las comprobaciones completas pasan dentro de la caja sobre una copia limpia.

M2 · Programa conductor orquestator-cli 3-4 días · depende de M0 y M1

La máquina de estados y las operaciones deterministas. El piloto usa run; el coordinador no entra.

  • Estado: fases, transiciones y libreta en ~/.orquestator/ESQ-123/state.json.
  • run: encadena start → check → review → ship → pr-review, aplica fix hasta agotar rondas, pide la migración antes de In validation y se detiene en Blocked/In validation.
  • Copia y espejo: copia sin remoto, espejo de la rama principal de solo lectura, importación de la rama y diferencias en tu copia principal.
  • Cajas: montajes por fase, directorio base de artefactos en solo lectura y overlays de escritura; estado y huella fuera.
  • Comprobaciones: estilo, tipos, pruebas con umbrales de cobertura, recorrido completo, RED, pruebas debilitados y lock de migraciones.
  • Propuesta: subir la rama, abrir la propuesta, cuerpo, comentarios, semáforo guard, filtrado de comentarios por autor y bloqueo de las automatizaciones de GitHub.
  • Migración: solo si la funcionalidad la lleva; aplicar tras aprobación, re-ejecutar el trabajo automático y verificar la huella.
  • Limpieza: retirar caja, copia y estado; comprobaciones de despliegue y sugerencia de vuelta atrás.
  • Pruebas: tabla de transiciones, --dry-run, pruebas con un cambio externo malicioso y con la traída del espejo.

Hecho cuando: cada comando acepta --dry-run sin efectos y run --dry-run recorre el flujo completo sobre una copia de juguete.

M3 · Perfiles de fase 2-3 horas · depende de M1 y M2

Tres perfiles con modelos distintos, resúmenes claros y el mismo formato de salida.

  • implementer, reviewer y pr-reviewer. Sin verifier: las comprobaciones son deterministas.
  • Sin enchufes de herramientas (MCP) en el piloto; la conexión solo si un perfil la necesita más adelante.
  • Modelo de nan distinto para el revisor y el revisor de la propuesta; el implementador usa el mejor de código.
  • Resúmenes: qué leer, qué producir, formato de los informes de revisión y cuándo parar y preguntar.
  • Prueba de humo con una tarea de juguete en una copia desechable.

Hecho cuando: una tarea de juguete produce resumen, implementación, informe de revisión y comprobaciones con los formatos esperados.

M4 · Piloto 1 tarea real · depende de M0-M3

Recorrer el flujo entero con una funcionalidad pequeña del backlog, no con una tarea inventada.

  • Elegir la funcionalidad y escribir la ficha con criterios positivos, negativos y límites; pasarla a Ready.
  • Ejecutar run y anotar tiempos e incidencias por fase.
  • Si la funcionalidad lleva migración, validar el trabajo automático migracion y migrate con la llave de edición.
  • Validar vídeo/capturas o local, integrar y confirmar el despliegue.
  • Revisión de lo ocurrido: qué falló, qué cambiar en el conductor y en los resúmenes; actualizar el plan.
  • Comprobar casos negativos, trazabilidad criterio→prueba, umbrales de cobertura y revisión por el agente y por ti.

Hecho cuando: la propuesta está integrada, las comprobaciones verdes y no hay pasos manuales no previstos (o están documentados).

M5a · Copia temporal 2-3 días · depende de M4

Una copia de la web por rama, con su propia base de datos y sus propias fotos, para validar desde el móvil.

  • Subir wrangler a 4.135.0 o superior; tu ordenador usa el de devDependencies, un solo número.
  • Copias por rama con wrangler preview, base de datos y almacén propios, URLs predecibles para los dos Workers.
  • Datos sembrados, migración de la base de datos de la copia antes de publicarla, limpieza al cerrar la propuesta.
  • Access sobre las URLs de la copia temporal; verificar el paso frontal↔API. Dominio propio opcional.
  • Enlace de la copia en el cuerpo de la propuesta y en Linear.
  • Orden: migración de la copia antes de ship; migración real tras tu aprobación y antes de In validation.

Hecho cuando: una propuesta obtiene una copia aislada con datos sembrados y se puede validar desde el móvil.

M5b · Automatización 1-2 días · depende de M5a

Que la cola pueda correr sola y que la revisión de la ficha tenga su bucle.

  • watch como servicio de usuario (systemd con loginctl enable-linger) o timer; al detectar la integración, ejecuta clean.
  • Revisor de la ficha: preguntas en comentarios, bloque orquestator-cli:acordado y sondeo de respuestas.
  • Trabajo automático guard del robot de comprobaciones: lee la lista de la rama principal y falla si hay zonas delicadas sin el semáforo guard.
  • Conexión de herramientas (MCP) solo si un perfil la necesita; por defecto, ninguno.
  • Si el piloto no llevó migración, construir migrate y probarlo con una migración de juguete.
  • Evaluar si hace falta coordinador (Nivel 2); si no, run sigue siendo el camino.
  • Medir el tiempo de una tarea de principio a fin.

Hecho cuando: la cola corre sola y una propuesta con zonas delicadas sin el semáforo guard no se puede integrar.

M6 · Después del piloto a decidir · depende de M5b

Decisiones que se toman con datos del piloto, no antes.

  • Evaluar omp como ejecutor si Hermes no cumple la adherencia (mismo resumen y comprobaciones).
  • Canales de aviso (Telegram/ntfy) y latidos, si aportan.
  • notas de decisiones (ADR) para la arquitectura real; revisión final de AGENTS.md.
  • Revisar cobertura: objetivo 60% en api/web y decidir si se suben los umbrales.
  • Revisar el paralelismo: cuántas tareas a la vez con 16 núcleos y 30 GiB.
Primero

Los primeros cinco minutos de M0

  1. gh auth login y comprobar con gh auth status.
  2. Arrancar Docker y probar docker run --rm hello-world.
  3. Preparar la revisión previa a hacer público el repo: correos del historial, recetas del libro y gitleaks.
  4. Crear el workspace de Linear y la llave de API.
  5. Crear la llave de Cloudflare de solo lectura para el trabajo automático migracion y la de edición para el conductor.
Riesgos

Lo que hay que verificar

  • Que la llave de solo lectura de Cloudflare pueda listar las migraciones. Si no, se usa el plan B.
  • Que wrangler preview soporte la base de datos, el almacén de fotos y Access.
  • Que haya modelos de nan suficientemente distintos para los dos revisores.
  • Las propuestas de forks no reciben secretos; el trabajo automático migracion queda bloqueado hasta que un responsable lo re-ejecute.
  • M2 son 3-4 días con el alcance recortado; con watch y migrate completos, 4-6.

08 · Glosario

Traductor de palabras

Si una palabra no está aquí, se puede explicar sin ella. Este glosario existe para que el resto del documento no tenga que repetir definiciones.

Tarea / issue
La ficha donde escribes qué quieres y cómo se sabrá que está bien.
Spec
Los criterios de la ficha: un caso normal, uno que debe fallar y uno al límite.
run
El conductor. Prepara la copia, llama a las fases en orden y se detiene cuando hace falta una persona.
Copia / clon
Una copia de trabajo del repositorio, con su propia historia, sin conexión directa con tu repositorio principal.
Caja / contenedor
Un entorno aislado con las herramientas de una fase. No ve tus llaves ni tu repositorio principal.
Libreta / estado
El fichero de tu ordenador que guarda la fase, las rondas y la huella aprobada. No vive en la copia.
Semáforo / commit status
Una marca de «verde» o «rojo» atada a una versión exacta del código. Si cambia el código, la marca anterior no vale.
Huella / hash
Un resumen único de un cambio o de una migración. Sirve para saber si algo cambió.
Aprobación en terminal
Un sí que das en una terminal interactiva, no desde el agente. Así el ayudante no puede aprobar por ti.
PR / propuesta
Una rama con cambios que se propone integrar en la rama principal. No se integra sola.
CI / robot de comprobaciones
El sistema que ejecuta estilo, tipos, pruebas y recorrido completo en cada propuesta.
Migración
Un cambio en la base de datos. Se aprueba aparte, se aplica con una llave limitada y no tiene vuelta atrás automática.
Copia temporal / preview
Una versión de la web solo para una propuesta, con su propia base de datos y sus fotos. Se borra al cerrar.
Llave / token
Una credencial limitada. La de solo lectura no puede cambiar nada; la de edición solo toca lo necesario.
RED
El prueba nuevo falla antes del arreglo. Así se sabe que la prueba prueba algo real.
Umbral de cobertura
El mínimo de código que deben tocar los pruebas. Los umbrales solo suben.
MCP
Un enchufe de herramientas externas. En el piloto no se usa; se añadirá solo si un perfil lo necesita.
Merge
Integrar la propuesta en la rama principal. Es el único camino a la web publicada y siempre lo haces tú.
Rollback
Volver a la versión anterior si el despliegue falla. La limpieza lo sugiere; no lo hace sola.
